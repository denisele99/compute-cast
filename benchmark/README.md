# Compute Cast benchmark runner

The same trusted runner is used in two places:

- the **local package** you download from Compute Cast, and
- the **Nebius AI Cloud container image**.

It measures **speed and memory** of complete GPT-2-style training updates on **one GPU**. It runs
only the model code in `models/`, selected through `model_registry.py`. It never imports uploaded
code, never installs packages, and never downloads model code or weights.

| File | Purpose |
| --- | --- |
| `benchmark.py` | Runner: validates the config, builds the model, times updates, writes `results.json` + `benchmark.log` |
| `model_registry.py` | Config schema, limits, Hugging Face allowlist and parameter formula; also used by the Compute Cast backend |
| `models/decoder.py` | Trusted GPT-2 decoder implementation (learned positions, tied LM head, FP32 math attention) |
| `benchmark_config.json` | Your validated configuration. It is generated by Compute Cast and is data only, never code |
| `requirements.txt` | Pinned dependency (`torch==2.5.1`) |

## What is measured and what is not

**Measured.** Complete optimizer updates are timed between GPU synchronisations, after warm-up
updates. Each update is a forward pass, FP32 loss and backward pass for every accumulation
microbatch, followed by an AdamW step.

- Inputs are synthetic random token ids, generated before timing starts.
- Memory figures are the peak allocated and reserved values from PyTorch's caching allocator.

**Excluded.**

- Process start-up, imports and model construction. These are reported separately as `durations.startup_seconds`.
- Real dataset loading and tokenisation.
- Evaluation and checkpointing.
- Cloud provisioning, image pull and scheduling.

Random weights and synthetic inputs say **nothing about model quality**.

**Throughput units.** `tokens_per_second` is calculated as:

measured updates × accumulation steps × microbatch size × sequence length ÷ measured training seconds

## Run locally

You need Python 3.10+, an NVIDIA GPU with native BF16 support, and a CUDA build of PyTorch 2.5.1.

1. Create a virtual environment.

   ```bash
   python -m venv .venv
   ```

2. Activate it.

   ```bash
   source .venv/bin/activate
   ```

3. Install PyTorch. Pick the CUDA wheel that matches your driver from
   https://pytorch.org/get-started/locally/; for example:

   ```bash
   pip install torch==2.5.1 --index-url https://download.pytorch.org/whl/cu124
   ```

4. Run the benchmark.

   ```bash
   python benchmark.py --config benchmark_config.json
   ```

No Nebius or other cloud credentials are needed. The runner detects the actual GPU and uses
device 0 only. A configuration with more than one GPU is rejected.

When it finishes, upload or paste `results.json` in Compute Cast (**Benchmark → Import results**).
The file is validated as untrusted data and compared with the prediction for the same
configuration.

### Options

| Option | Default | Meaning |
| --- | --- | --- |
| `--config` | `benchmark_config.json` | Configuration to run |
| `--output-dir` | `.` | Where `results.json` and `benchmark.log` are written |
| `--max-seconds` | `300` (env `BENCH_MAX_SECONDS`) | Runner limit, including start-up and warm-up (1–3600) |
| `--cpu-smoke` | off | Functional check on CPU, see below |

### CPU smoke test (functional check only)

```bash
python benchmark.py --config benchmark_config.json --cpu-smoke
```

This checks that the configuration builds and trains on CPU, with any torch 2.5.1 build. Results are
marked `"smoke_test": true` and are **not valid** CUDA performance or memory measurements.
Compute Cast shows them as a smoke test and never uses them for calibration. Use a tiny
configuration: full GPT-2 shapes are slow on CPU.

### Exit codes

| Code | Status |
| --- | --- |
| 0 | succeeded |
| 1 | runtime error |
| 2 | invalid configuration (nothing ran) |
| 3 | out of memory |
| 4 | runner time limit reached |
| 5 | unsupported hardware (no CUDA GPU without `--cpu-smoke`, or no BF16 support) |

`results.json` is written in every case. If the run failed, it includes `failure.type` and `failure.message`.

## Container image (maintainers)

The image contains only the files above and no configuration or credentials. Nebius injects the
config at `/config/benchmark_config.json`, and results go to `/results`, a mounted bucket path.

> **Status:** the Dockerfile has **not** been built or run as part of this change, because Docker
> was not available in the development environment. Build and test it yourself before configuring
> the backend.

All of the steps below run from `benchmark/`.

1. Build the image.

   ```bash
   docker build -t compute-cast-bench:0.1.0 .
   ```

2. Run a local CPU smoke test with the example config. Bind-mount the config directory and an
   output directory.

   ```bash
   mkdir -p /tmp/cc-results && cp benchmark_config.example.json /tmp/benchmark_config.json
   ```

   ```bash
   docker run --rm -v /tmp/benchmark_config.json:/config/benchmark_config.json:ro -v /tmp/cc-results:/results compute-cast-bench:0.1.0 --config /config/benchmark_config.json --output-dir /results --cpu-smoke --max-seconds 600
   ```

3. Optionally, run a GPU test on a machine with the NVIDIA Container Toolkit installed.

   ```bash
   docker run --rm --gpus 1 -v /tmp/benchmark_config.json:/config/benchmark_config.json:ro -v /tmp/cc-results:/results compute-cast-bench:0.1.0
   ```

4. Publish the image to your Nebius Container Registry. Replace `<registry-id>` with your own.

   ```bash
   docker tag compute-cast-bench:0.1.0 cr.eu-north1.nebius.cloud/<registry-id>/compute-cast-bench:0.1.0
   ```

   ```bash
   docker push cr.eu-north1.nebius.cloud/<registry-id>/compute-cast-bench:0.1.0
   ```

   Use your region's hostname: `cr.<region>.nebius.cloud`, for example `cr.eu-north1`,
   `cr.us-central1` or `cr.uk-south1`. Log in first with `nebius registry configure-helper`, which
   sets up the Docker credential helper.

5. Pin the image by digest. Use an **immutable** reference in the backend, never a mutable tag.

   ```bash
   docker inspect --format '{{index .RepoDigests 0}}' cr.eu-north1.nebius.cloud/<registry-id>/compute-cast-bench:0.1.0
   ```

   Set `BENCH_IMAGE=cr.eu-north1.nebius.cloud/<registry-id>/compute-cast-bench@sha256:<digest>` on
   the backend. For full reproducibility, also pin the `FROM` line by digest; see the comment in
   the `Dockerfile`.

6. Configure registry access. A Nebius Container Registry in the **same project** as the jobs
   needs no pull credentials. For any other private registry, store the username and password in a
   SecretStash (formerly MysteryBox) secret, and set the backend's `NEBIUS_REGISTRY_SECRET_VERSION`
   to that secret version's ID. The SDK docstring names the keys `REGISTRY_USERNAME` and
   `REGISTRY_PASSWORD`, while the CLI docs use `registry_username` and `registry_password`, so check
   which one works on the first job. The backend never sends registry passwords itself.

When you change `benchmark.py`, `model_registry.py` or `models/`, bump `BENCHMARK_CODE_VERSION` in
`model_registry.py`. Then rebuild the image, push it, and update `BENCH_IMAGE` to the new digest.
The backend and the image must use the same registry version.
